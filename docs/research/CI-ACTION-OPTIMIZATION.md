# CI and ExUnit optimization research

> **Research and measurement record.** This records current evidence and source-backed options. A scoped test-only graph index is under exact-lane CI review; workflow policy and required checks remain unchanged.

**Date:** 2026-11-02
**Scope:** Fablebook GitHub Actions, the measured core/floor Mix test path, graph profiling, caching, scheduling, timeouts, ExUnit concurrency, and CI timing evidence.

## Recommendation

Keep both exact runtime lanes and their required PR checks. Fablebook already runs `core`, `floor`, Dialyzer, and security independently, then joins their results at `ci-gate`. The local profile found a specific repeated edge scan in pending caller-chain construction; a one-time map reduced the measured core graph phase by about 87% across two paired runs, while preserving inventory identities and existing rejection controls. The test-only change is awaiting current-head core/floor CI before it can be treated as a retained improvement. Do not move checks off PR CI, add a path skip, broaden caches, or add a dependency based on timing alone.

The recommendations below distinguish repo measurements from inference. References to GitHub and Elixir behavior point to their official documentation or source.

## Fablebook's timing and required guarantee

**Direct repo evidence:** [`.planning/CI-PERFORMANCE.md`](../../.planning/CI-PERFORMANCE.md) records an exact-head CI run where the core test command took 730 seconds (12m10s; 748 seconds for its job) and the floor test command took 689 seconds (11m29s; 715 seconds for its job). An earlier recorded run put core at 7m53s and floor at 10m16s. In the earlier run, setup was approximately 9–12 seconds per job, while the floor test command itself took 9m56s. Its installed-runtime receipt measured `graph_ms=370589` (6m11s); `xref_ms` was about 8s and source scanning about 0.1s. The run also produced a 63.4 MB floor log. These are run-specific observations, not a controlled before/after benchmark.

**Direct repo contract:** [`ci.yml`](../../.github/workflows/ci.yml) runs `mix ci` on core Elixir 1.20.4 / OTP 29.1.2 and a separate floor job on Elixir 1.18.5 / OTP 27.3.4.9 against `mix.floor.lock`; the core pins are in [`.tool-versions`](../../.tool-versions) and floor pins in [`.tool-versions.floor`](../../.tool-versions.floor) (the workflow setup action currently passes the same floor versions directly). The floor job compiles with warnings as errors, compiles again with `--no-optional-deps --force`, and runs the test suite with `prod_guard` included. Both jobs are dependencies of the always-run `ci-gate`, as are Dialyzer, security, and the conditionally required nightly job. Core `mix ci` includes format, dependency-lock hygiene, forced compile, Credo, the compile-connected Xref graph, docs, and tests (including `prod_guard` and `release`). The supporting test selects the exact runtime and lock for the lane and records exact installed-runtime evidence; see [`mix.exs`](../../mix.exs), [`SweepEvidence`](../../test/support/sweep_evidence.ex), and [`tier_sweep_test.exs`](../../test/contract/tier_sweep_test.exs).

**Inference:** With one recorded graph phase taking 6m11s and setup taking seconds, changing dependency caching is unlikely to move the critical path materially unless new comparable runs show cache restore or compilation has become significant. The core and floor graph work must stay lane-specific: runtime, dependency lock, and installed OTP contents differ, and the receipt binds those identities. Reusing one lane's graph or receipt for the other would invalidate the lane proof.

## Profile-backed test-only candidate

**Direct repo evidence:** On the core lane, the graph contained 236,176 edges and 1,078 pending MFAs. The old caller-chain construction scanned the edge list for each path hop. Two focused profiles measured graph time at 151.014 s and 189.763 s; the indexed implementation measured 19.455 s and 25.130 s in paired runs. The optimized graph phase is therefore about 87% faster in these local runs. The full indexed tier-sweep module also produced a 27.680 s graph profile. A matched inventory comparison found the same pending-MFA keys and all non-path inventory rows.

**Observed output caveat:** Caller-chain arrays varied between independent runs with the old code (70 pending rows changed) and the indexed code (31 changed). This means independent receipt hashes cannot establish byte-for-byte equality for those paths. The focused fixture covers the tie rule, duplicate edges, exact start arity, fallback, and missing-edge behavior. It does not assert that a separately constructed graph selects the same witness path on every VM invocation.

**Local verification:** The untagged core tier-sweep module passed 53 tests. The focused index fixture passed on core and floor (one selected, 52 excluded in each lane), including comparison against the previous scan's duplicate and sort behavior.

**Recommendation (inference):** Keep this narrow test-only index if PR CI passes on both exact lanes. It removes repeated work without changing the receipt schema, lane-specific graph, failure checks, workflow, or dependency tree. Measure the core/floor PR job durations against the current-main run before claiming end-to-end CI savings; graph-phase improvement is not itself a full job-time measurement. If the resulting receipts expose the existing path variation as a concern, address deterministic witness selection in a separate change with its own acceptance criteria.

## Findings and options

### 1. Cache correctness and security

**Direct repo evidence:** [`.github/actions/setup/action.yml`](../../.github/actions/setup/action.yml) restores `deps` and `_build` from an exact key containing runner OS/architecture, resolved OTP and Elixir versions, `MIX_ENV`, and the selected lockfile hash (`mix.lock` or `mix.floor.lock`). It uses split restore/save actions and saves only on `main` after a miss. The Dialyzer PLT uses a separate key containing OS, architecture, toolchain-file hash, and `mix.lock` hash, and also saves only on `main`.

**Official source facts:** GitHub documents cache keys and scoped fallback behavior; a partial `restore-keys` match restores the most recently created matching cache. Cache entries are not signed or verified, restored contents can affect subsequently executed files, and pull-request authors can read base-branch caches. GitHub recommends not storing secrets in cache and limiting cache writes to trusted triggers. [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)

**Recommendation (inference):** Keep the exact lane/toolchain/environment/lock keys and trusted-branch saves. Do not add broad restore prefixes that can silently select a cache from another lock, runtime, or environment. Cache only regenerable dependency/build data, never credentials. If a cache change is considered later, first compare repeated exact-key hit rates and the separate restore, dependency compile, and test timings; the existing setup duration does not justify widening the cache now. The current policy already has the useful trust boundary: ordinary PR runs can consume compatible caches but do not publish the canonical `main` cache.

### 2. Job dependencies and concurrency

**Official source facts:** GitHub starts jobs without `needs` dependencies independently; `needs` makes a job wait for its prerequisite and skips it after a prerequisite fails unless the dependent job's condition handles that result. Concurrency groups serialize runs/jobs in the same group; `cancel-in-progress: true` cancels an active member, and a new pending run replaces an older pending run by default. [Workflow syntax: `needs` and `concurrency`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)

**Direct repo evidence:** Core, floor, Dialyzer, and security have no dependency edges between them. The gate alone waits for their outcomes (plus the nightly condition). Workflow concurrency groups distinguish pull requests by PR number and enable cancellation only for pull requests. The scheduled jobs use off-hour minute values, `17` and `23`, rather than the top of the hour.

**Recommendation (inference):** Preserve the independent jobs and the single gate. Adding a `needs` edge between either lane and another required job would extend the critical path without changing what the gate proves. Preserve PR cancellation: stale runs for the same PR are replaceable, while completed current-head checks remain required. Do not split the tier-sweep graph into dependent setup/graph/test jobs just to parallelize steps unless a benchmark shows a net gain; transferring or rebuilding its lane-bound evidence has its own cost and correctness surface.

### 3. PR, schedule, and manual dispatch

**Official source facts:** `schedule` runs against the latest commit on the default branch; GitHub warns it may be delayed or dropped during high Actions load, especially at the start of an hour. `workflow_dispatch` is available when the workflow file exists on the default branch. [Workflow syntax: schedule and dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [Troubleshooting scheduled workflows](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)

**Direct repo evidence:** PR and main pushes run the required core and floor jobs. The daily schedule runs the nightly consumer smoke; the weekly schedule runs the timing/shape health work. A manual dispatch also enables the nightly and health jobs in addition to the ordinary workflow jobs. The CI health script samples only pull-request runs when calculating its seven-day p50/p95, so dispatched and scheduled work does not enter that sample. See [`ci.yml`](../../.github/workflows/ci.yml) and [`bin/ci_health`](../../bin/ci_health).

**Recommendation (inference):** Retain PR coverage for the core/floor contracts and security checks. Keep scheduled/manual work as supplemental checks and recovery/diagnostic paths; do not treat them as replacements for current-head PR evidence. For a comparable latency measurement, use the PR path and compare several runs on the same code shape. A manual dispatch intentionally exercises extra jobs, so its total duration is not a like-for-like PR latency number. The current schedules already avoid minute zero.

### 4. Timeout and runner constraints

**Official source facts:** `timeout-minutes` sets the job cancellation bound (default 360 minutes); GitHub-hosted jobs also have a maximum execution limit. The public-repository standard `ubuntu-24.04` image is a four-CPU, 16 GB RAM, 14 GB SSD x64 VM; private-repository standard capacity for the same label is two CPUs and 8 GB RAM. [Job timeout syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [GitHub-hosted runner specifications](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [Actions limits](https://docs.github.com/en/actions/reference/limits)

**Direct repo evidence:** Core and floor use `ubuntu-24.04` with `timeout-minutes: 15`. The slowest recorded job in the evidence above took 748 seconds, leaving about 152 seconds before that workflow timeout. The repo's weekly health budget targets p50 ≤420 seconds and p95 ≤600 seconds over at least 10 eligible PR runs; recent runs exceeded that budget, so the measured path needs profiling rather than relying on the target as if it were already met.

**Recommendation (inference):** Do not lower the 15-minute timeout. Its headroom is only about 2.5 minutes over the recorded slow core job, so compare several recent job durations and distinguish queue time from runner execution before changing it. If legitimate runs continue to approach the cap while profiling/fixes are in progress, a larger bounded timeout is a reliability decision, not a speed optimization; document the chosen margin. Do not select a larger runner without a CPU/memory profile and a measured wall-time comparison. The local receipt attributes most measured time to graph work, but available records do not establish whether the runner is CPU-, memory-, disk-, or output-bound.

### 5. ExUnit parallelism and shared setup

**Official source facts:** ExUnit `async: true` runs modules concurrently with other modules, not tests inside a module; it is intended only for tests that do not mutate global state. `setup_all` runs once before that module's tests and passes its context to them. Mix `--max-cases` limits test modules running asynchronously, defaults to twice online schedulers, and `--partitions` distributes test files among separate Mix test processes. `mix test --slowest` and `--slowest-modules` automatically enable `--trace`; trace mode forces `--max-cases 1` and sets test timeouts to infinity. [ExUnit.Case source at the core version](https://github.com/elixir-lang/elixir/blob/v1.20.4/lib/ex_unit/lib/ex_unit/case.ex), [Mix test docs for Elixir 1.20](https://mix.hexdocs.pm/1.20.4/Mix.Tasks.Test.html)

**Direct repo evidence:** `Fablebook.Contract.TierSweepTest` is `async: false`, and its `setup_all` calls `build_graph()` once and shares that graph as test context. `build_graph/0` already measures monotonic-time subphases for discovery, BEAM inspection, source scanning, Xref work, and a total graph duration. The `InstalledOtpReceiptTest` module is also `async: false`; tests exercise named Xref servers, filesystem evidence, and lock-bound receipt validation. See [`tier_sweep_test.exs`](../../test/contract/tier_sweep_test.exs) and [`installed_otp.ex`](../../test/support/installed_otp.ex).

**Recommendation (inference):** Do not change these modules to `async: true` or add test partitions as a first-line speed tweak. Enabling async does not parallelize tests inside the large tier-sweep module, while running it alongside other CPU/memory-heavy tests could add contention. Partitioning distributes files rather than splitting this module's test list; it can add VM/setup overhead and should be benchmarked end to end. Keep `--slowest` for focused diagnosis, not representative CI timing: its implicit serial mode and disabled test timeouts change the execution being measured. First use the existing graph receipts, then add finer monotonic measurements around graph substeps whose cost remains unclear. Any eventual bounded parallel map must preserve sorted, exact inventories and deterministic failure behavior in both lanes.

### 6. Workflow timing and evidence instrumentation

**Official source facts:** GitHub logs expose per-step time, job runner details, and workflow job data through its Actions APIs. `GITHUB_STEP_SUMMARY` is a built-in per-step Markdown file that appears on the workflow summary page; the workflow jobs API exposes job timestamps and logs. [Workflow run logs](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs), [Job summaries](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands), [Workflow jobs REST API](https://docs.github.com/en/rest/actions/workflow-jobs)

**Direct repo evidence:** `bin/ci_health` already uses the workflow jobs API to compute elapsed time from run creation until `ci-gate` completion, records rolling p50/p95, and writes a short report to `GITHUB_STEP_SUMMARY`. That elapsed time includes queue time, which is useful for feedback latency but is not the same as runner execution time. Tier-sweep receipts already include detailed counts, lock/runtime identity, and phase timings, but currently the test emits all receipt lines to stdout; prior logs reached roughly 55–63 MB.

**Recommendation (inference):** Keep the rolling health job and its timing budget. For follow-up profiling, report both end-to-end run latency (created → gate completed) and runner/job duration (job started → completed), so queueing does not get mistaken for slower Elixir work. Add only compact per-lane summary values (toolchain, lock digest, phase durations, test result) to job summaries. If the full receipt is moved out of the log, retain the same validated receipt as a downloadable run artifact and keep a regression check proving its row counts, identity, digests, and verdict match; do not simply suppress the rows or weaken the receipt tests. GitHub's built-in timing and summary surfaces are sufficient for the first measurement pass, without another telemetry dependency.

## Practical next measurements

1. Collect several comparable PR runs and separate queue-to-start delay, setup/cache restore, dependency compile, test step, and total graph duration for both core and floor.
2. Within `build_graph`, time the large traversal/projection and evidence-generation segments that are currently grouped under `graph_ms`. Preserve the exact receipt and verdict while comparing outputs and timings.
3. If runner time still exceeds the budget after graph profiling, evaluate one isolated optimization at a time against both exact lanes, including the complete CI critical path. Keep setup/cache changes only if repeated measurements show a material gain.
