# UI-first roadmap research: Phoenix paths to the first real scenario

**Date:** 2026-11-20  
**Purpose:** Primary-source technical research for the requested UI-first roadmap review. This is research, not a phase plan, gate decision, or authorization to implement.

**Current evidence context:** v0.6 is complete; candidate remains null and the aggregate gate remains open. The recorded selected family has seven proposed MFAs against a 1,756-function complement; four source gaps remain and five source requests are closed. The current package route is a plain-text placeholder, and this checkout has no `hosts/` apps, authored Fablebook Books, or rendered product UI. These are carried facts from the current [state](../STATE.md), [v0.6 reconciliation research](2026-11-19-v0.6-guard-scope-reconciliation.md), and [source discovery](2026-11-19-ex177-source-discovery.md), not a fresh audit in this note.

## Finding

The shortest credible path to visible Fablebook product work is one host-rendered screen built from a presentational Phoenix function component, a small set of compiled scenario inputs, and deterministic in-memory sample data. Mount a small LiveView route in a real host when the screen needs interaction; use a controller route for a screen that is purely static. Reuse the host's layout, CSS, fonts, scripts, hooks, and CSP. This gives a real Phoenix render without a database, service layer, complete logistics application, or new runtime dependency.

For the first slice, keep the route and scenario selection fixed in compiled code. A small screen can show two or three named situations and a simple local UI action, while the Book records the screen, its scenarios, and a Journey's steps. Make the UI clear about which actions are illustrative; do not suggest that shipment data was persisted. General catalog discovery, arbitrary Controls, full workflow simulation, the whole Logistify family, and cross-product tooling can follow after an actual screen exists.

**The existing guard-aggregate gate remains open and blocks the Walking Skeleton.** This research does not recommend changing it, close it, or authorize work across it. The implementation options below are conditional technical findings; the owner decision and typed prerequisite remain separate. See the existing [UI-first gate review](2026-11-20-ui-first-gate-review.md), [current roadmap](../references/PRODUCT-ROADMAP.md), [state](../STATE.md), and [planning gates](../references/PLANNING-GATES.json). This note preserves those records rather than replacing them.

## Phoenix implementation options

| Approach | What it provides | Cost and boundary | Fit |
|---|---|---|---|
| **Host LiveView with a presentational component** | The route sends ordinary HTML on the initial request, then can connect for events. This renders through the host endpoint and can use the host's root layout, while the host's LiveView handles a small set of local transitions. ([LiveView lifecycle](https://phoenix-live-view.hexdocs.pm/Phoenix.LiveView.html)) | No database or new UI runtime is required. Keep `mount/3` and events deterministic. Do not turn URL parameters into module names, atoms, templates, or code. | **Recommended after the gate permits the slice.** Best for a UI that needs to show and exercise a small number of scenario transitions. |
| **Phoenix controller + HEEx function component** | A regular request renders a component through the host's HTTP pipeline without opening a LiveView socket. | Good for a static Primitive, Pattern, or fixed Screen. Browser-only controls need ordinary links/forms or a later LiveView enhancement. Use `Phoenix.ConnTest` for the HTTP response. | Lowest-complexity first render if the initial screen has no interactive transition. |
| **Mount phoenix_storybook in the host** | A mature in-app explorer can be available quickly. Its stories can describe function components, LiveComponents, pages, and examples; dev compilation is lazy. ([setup](https://phoenix-storybook.hexdocs.pm/setup.html), [story types](https://phoenix-storybook.hexdocs.pm/PhoenixStorybook.Story.html)) | It adds a dependency and expects its own JS and CSS bundles; the setup guide explicitly says these are not the app's `app.js` and `app.css`. Its components share the Storybook LiveSocket and document context by default. ([sandboxing guide](https://phoenix-storybook.hexdocs.pm/sandboxing.html)) These choices need explicit comparison with Fablebook's host-pipeline fidelity, isolation, CSP, and dependency decisions. | Use as source-level prior art or a bounded local comparison. It is not required for Fablebook's first screen and should not become a shortcut around Fablebook's own product contract. |

Phoenix's own generated router shows development routes inside `if Application.compile_env(:app, :dev_routes)`, under a `/dev` scope; the template warns that LiveDashboard in production needs authentication and admin restriction. ([Phoenix router template](https://github.com/phoenixframework/phoenix/blob/main/installer/templates/phx_web/router.ex)) If a host scenario route is dev/test-only, use that compile-time guard and still verify the production route map and release configuration. A path named `/dev` is not a security control, and the compile-time guard by itself does not prove every development-only module or artifact is absent from a release.

If a route is intentionally reachable by authenticated users in a production application, Phoenix requires authentication/authorization for both the regular request pipeline and the LiveView mount; use the matching `on_mount` protection as well as request plugs. ([LiveView security model](https://phoenix-live-view.hexdocs.pm/security-model.html)) For Fablebook itself, the accepted project contract keeps stories and canon out of production, and the current `Fablebook.Router` rejects a mount reachable in a production build. The current implementation still returns a text placeholder; it has no rendered host UI. See [router](../../lib/fablebook/router.ex) and [placeholder](../../lib/fablebook/placeholder.ex).

## Static Books and trusted inputs

This direction matches existing Fablebook decisions rather than requiring a new story DSL:

- [ADR 0002](../../docs/adr/0002-scenarios-are-plain-functions.md) already defines arity-zero scenario functions as data and arity-one functions as HEEx composition. Screen and Area subjects are presentational function components; their LiveView owns mount, params, events, and data loading. Rich slots use captured functions, never strings interpreted as markup.
- [INT-20261120-08](../intent/sources/2026-11-20-08-define-showcase-books-not-full-demo-apps.md) says Logistify Books capture representative screens, workflows/Journeys, situations, and key interactions. It does not require full business applications or real logistics backends. [ADR 0020](../../docs/adr/0020-host-apps-dogfood.md) already specifies host apps without Ecto.
- A Book can initially be a fixed, reviewed set of scenario declarations plus fixture structs/maps in compiled host code. Each scenario has a meaningful named situation and believable, fictional data. A Journey can link scenario addresses and describe a local UI action between them; no database transaction or external service is needed to represent that view of the flow.
- Keep scenario values literal and bounded. For any later controls, parse URL/event strings against declared options or presets and return a known typed value. A fixed string-to-module table is safer than constructing module names from request data. Never use `Code.eval_*`, `EEx.*_string`, runtime compilation, or `String.to_atom` for story input. This is an existing non-negotiable in [ADR 0004](../../docs/adr/0004-no-eval-no-new-atoms.md), not a new rule.

Phoenix LiveView's initial render is an ordinary HTML request before its socket connection; it can show the first scenario even if client-side behavior has not connected. `Phoenix.LiveViewTest` can render a function component and can exercise a LiveView event by selecting the actual bound element, so most first-slice contracts do not need a real browser. ([Lifecycle](https://phoenix-live-view.hexdocs.pm/Phoenix.LiveView.html), [LiveViewTest](https://phoenix-live-view.hexdocs.pm/Phoenix.LiveViewTest.html)) Storybook's own docs similarly treat each story as a defined initial component state and describe optional interaction tests for changes; use that as a conceptual pattern, not as an Elixir API recipe. ([Story args](https://storybook.js.org/docs/writing-stories/args), [interaction tests](https://storybook.js.org/docs/writing-tests/interaction-testing))

## Trust boundary and adversarial risks

Compiled story modules are trusted application code. They must come only from reviewed repository content and must never be selected, authored, compiled, or evaluated from a browser request. `phoenix_storybook` stories are `.exs` scripts; its current docs say dev loads them lazily from the UI. Lazy compilation is a developer-workflow property, not a reason to accept untrusted source. ([Story docs](https://phoenix-storybook.hexdocs.pm/PhoenixStorybook.Story.html))

The first user-controlled boundary should be as small as possible: fixed route, fixed story, fixed scenario, fixed fixture. On later slices, accept only known enum-like scenario IDs and declared literal/preset values; reject unknown keys and oversized values before rendering. Keep all IDs as strings until they match a known entry. Never derive PubSub topics from request parameters. These points preserve the direct input rules even while the broad guard aggregate remains open.

**Compile-time caveat found in adversarial review:** the existing public [`Fablebook.Router.fablebook/2`](../../lib/fablebook/router.ex) macro calls `Macro.expand(book, caller_env)` on the caller-supplied AST. Elixir documents that `Macro.expand/2` expands aliases and local/remote macros at compile time; it does not evaluate arbitrary expressions as runtime input, but macro expansion can run caller macro code. Therefore “fixed scenario data” alone does not settle this call boundary. Before a first host slice uses the public macro, explicitly define and test accepted `book` AST forms (prefer a literal module alias/reference and reject arbitrary macro expressions) or retain the risk as a blocker. See the [official Macro documentation](https://hexdocs.pm/elixir/1.18.1/Macro.html#expand/2) and the current [router implementation](../../lib/fablebook/router.ex#L35).

The `phoenix_storybook` history is useful security evidence. The project advisory describes a critical remote code execution bug in versions before 1.1.0 where client-supplied playground values were interpolated into HEEx text and evaluated; the issue was fixed in 1.1.0. This does **not** claim that current 1.5.0 has that vulnerability. It shows why Fablebook keeps browser values as typed data and does not generate/evaluate templates from them. ([GHSA-55hg-8qxv-qj4p](https://github.com/phenixdigital/phoenix_storybook/security/advisories/GHSA-55hg-8qxv-qj4p), [1.1.0 changelog entry](https://github.com/phenixdigital/phoenix_storybook/blob/main/CHANGELOG.md))

An isolated direct host route is a useful first render proof, but it is not yet proof of Fablebook's final Canvas fidelity. The accepted contract requires the Canvas to use the adopter's real pipeline and isolate the preview; see [ADR 0003](../../docs/adr/0003-iframe-canvas-through-host-pipeline.md) and the [North Star](../intent/NORTH-STAR.md). Do not claim CSS/font/hook/CSP parity from server-rendered HTML alone. Likewise, do not apply staged Fablebook or Logistify brand assets to the first UI until their destinations/rights and source decisions are resolved; see [Fablebook intake](../references/fablebook-brand-intake.md) and [Logistify intake](../references/logistify-brand-intake.md).

## Fidelity, accessibility, and visual checks

**Fidelity.** Start with the host's own layout and normal asset pipeline; avoid a separate `storybook.css`/`storybook.js` copy for the first Fablebook render. Load the same host fonts, CSS, JS hooks, and security headers that its real route uses. The future adversarial operator host remains valuable for nonce CSP, custom layout/tokens, hooks, and font regressions, but it need not be a complete demo application to capture screen scenarios. Host-level evidence is still required before claiming the full fidelity criterion.

**Accessibility.** Keep the existing WCAG 2.2 AA target. For the first screen, cover semantic names/roles, form labels where present, keyboard operation, visible focus, non-color status labels, and the project's narrow viewport. WCAG 2.2 requires a visible focus mode (2.4.7 AA) and a 24×24 CSS-pixel minimum pointer target or one of its stated exceptions (2.5.8 AA); WCAG also has separate contrast requirements. ([WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/), [Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible), [Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)) A vendored axe run catches some automated issues but does not establish good grouping, comprehension, or an accessible Journey by itself. Keep human visual and keyboard review for those questions; automated checks cannot judge the full experience. This complements the strict-by-default rules in [ADR 0024](../../docs/adr/0024-strict-by-default-with-waivers.md).

**Browser/visual checks.** Use fast `Phoenix.LiveViewTest` and pure renderer tests for the fixed scenario, route status, event transitions, and HTML contracts. Add one browser run only when the acceptance claim depends on actual browser behavior, such as host CSS/font loading, CSP, viewport layout, JS hooks, or a visual capture. The optional `phoenix_test_playwright` API supports screenshots and screenshot comparisons, so a browser runner can be evaluated without making it a runtime dependency for adopters. ([PhoenixTestPlaywright](https://phoenix-test-playwright.hexdocs.pm/PhoenixTest.Playwright.html)) Pin the browser/runtime and fixture data. A first-time `assert_screenshot` with no baseline saves one and passes, so the test must independently fail when the reviewed baseline is missing; a human must accept any changed baseline. ([baseline behavior in source](https://github.com/ftes/phoenix_test_playwright/blob/main/lib/phoenix_test/playwright.ex); [ADR 0011](../../docs/adr/0011-browser-runner.md))

## CI bottlenecks and bounded feedback

Repository evidence records two required Elixir lanes that run concurrently. Recent exact-head runs in [CI performance evidence](../CI-PERFORMANCE.md) take roughly 9–12 minutes to the required gate; the captured cost is mainly the lane-specific installed-OTP inventory graph and large evidence output, while setup is brief. That is a project-level baseline, not a measurement of a future UI test. The project already makes CI optimizations evidence-led and keeps both lanes and their contracts.

Recommended feedback order for a UI slice:

1. Run format/compile and the focused renderer or LiveView test first; these can catch malformed static story data without launching a browser.
2. Run the focused host smoke in a browser only for claims that a DOM test cannot establish (CSP, host assets, responsive layout, JS hook behavior, or screenshot evidence).
3. Keep the full existing required lanes and hosted receipt at the phase delivery gate. Do not add a screenshot per scenario or a full viewport/theme/localization cross-product to PR CI before determinism and maintenance cost are measured.
4. Measure browser startup, capture time, flake rate, and visual-diff review effort independently. Keep screenshots bounded to representative accepted renditions; never lower unrelated lane coverage or add a broad cache/concurrency change to make UI CI look fast.

This matches the existing operational rule to use throwaway/local checks for one-off questions and make recurring checks earn their maintenance cost ([CI performance policy](../CI-PERFORMANCE.md)). The current dependency contract already permits an optional browser feature while requiring adopters to need no Node; do not add a new default runtime dependency ([ADR 0018](../../docs/adr/0018-dependency-budget.md)).

## Directional sequencing for the roadmap

This is sequencing advice for later roadmap synthesis, not executable scope or a gate recommendation:

1. Preserve all current prerequisites and safety stops. The named Walking Skeleton remains behind the typed aggregate gate. Any proposed exception needs a separate explicit owner decision; this research supplies no gate-change recommendation.
2. Once permitted, make the first deliverable a visible route in the smallest real host, with one compiled Book entry, one presentational Screen or Area, a deterministic fixture, and a few named situations. ADR 0020 and the existing Walking Skeleton criteria still name both vanilla and adversarial hosts; this shorter checkpoint does not satisfy or replace those acceptance criteria. Verify direct rendering and production route exclusion.
3. Add only the small amount of navigation/state transition needed to inspect a Journey. Keep Book content as fixed scenarios and descriptions; do not build auth, logistics APIs, database models, job queues, or a complete application backend.
4. Build catalog discovery and URL addressing from that real example. Add Controls only after a concrete input boundary is specified and its no-eval/no-atom properties are covered.
5. Grow from the first screen into the requested Logistify Books and their Journeys, with distinct jobs and screen constraints. Keep source brand books, applied canon, and Fablebook Books as separate artifacts. Treat source guidance as input, not implemented product behavior.
6. Expand visual baselines, grid isolation, full state coverage, and other browser checks only as their product surface exists and a measured runner decision supports them.

The existing rolling roadmap and accepted ADRs remain the sources for the wider product sequence. This research does not assign new phase numbers or claim that a UI screen, Book, or demo has shipped.
