### WR-02: Newly reached Logger/ExUnit function names can still bypass family records

**Classification:** WARNING
**File:** `test/contract/tier_sweep_test.exs:774-780, 2951-2977`

**Issue:** The correction makes `@logger_family_universe` independent from the specs, resolving the reported omission of a known MFA. However, `@logger_family_functions` is still only the finite set of `{module, function}` pairs in that universe, and `assert_logger_audit!/6` filters both reached exports and explicit tier/exclusion roots through that set. A newly reached export with a new function name in a covered Logger/ExUnit module can therefore be tiered and remain absent from the family records: it is omitted from `reached_family` and `explicit_family_roots`, while the pinned expected records remain unchanged. Reproduction: add a new exported front such as `Logger.public_format_front/1` that calls a banned sink, add that MFA to the guard tier, but omit it from the pinned universe/specs. Since the tier root is not itself added to `reached` and the explicit-root filter excludes its unknown function name, the audit can still compare equal without a semantic record for the new front.

**Fix:** Define the bounded Logger/ExUnit module boundary independently of the function records, then compare every reached exported MFA and every explicit tier/exclusion root in those modules against the family records and expected universe. Keep the existing exact per-lane source checks for each recorded MFA.
