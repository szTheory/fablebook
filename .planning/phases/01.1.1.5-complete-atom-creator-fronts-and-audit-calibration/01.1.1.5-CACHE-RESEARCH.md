# Mix, Hex, and Docker cache locations

Checked 2026-11-02 against current official Elixir/Mix, Hex, and Docker documentation.

## Locations

- **Mix global home:** `~/.mix` by default. Mix stores global configuration and scripts here; archives default to `~/.mix/archives`. `MIX_HOME`, `MIX_ARCHIVES`, and opt-in `MIX_XDG` can change these locations. [Elixir Mix environment variables](https://github.com/elixir-lang/elixir/blob/main/lib/mix/lib/mix.ex#L2645-L2723)
- **Hex home:** `~/.hex` by default. Hex describes `HEX_HOME` as the directory for its cache and configuration; `HEX_HOME` takes precedence over opt-in `MIX_XDG`. [Hex `mix hex.config`](https://hex.hexdocs.pm/Mix.Tasks.Hex.Config.html)
- **Project dependency sources and build products:** `deps/` and `_build/<env>/` by default. Mix documents `MIX_DEPS_PATH`, `MIX_BUILD_ROOT`, and `MIX_BUILD_PATH` overrides; target/environment settings also affect build paths. [Mix.Project paths](https://mix.hexdocs.pm/Mix.Project.html)

With separate checkouts running under the same user home, the default global `.mix` and `.hex` paths are shared; each checkout's default `deps/` and `_build/` paths remain under its own project directory. This follows from the documented defaults, not a separate Hex concurrency guarantee.

## Docker cache behavior and Hex concurrency

BuildKit `RUN --mount=type=cache` provides a persistent package/compiler cache. Its optional `id` distinguishes caches; `sharing` defaults to `shared`, which allows concurrent writers. `private` gives concurrent writers separate mounts, while `locked` makes a second writer wait. Docker says package managers have different locking needs and advises checking the package manager's requirements. [Dockerfile cache mounts](https://docs.docker.com/reference/dockerfile/#run---mounttypecache) · [Docker cache guidance](https://docs.docker.com/build/cache/optimize/#use-cache-mounts)

Hex documents where its cache/configuration live, but the reviewed official Hex docs do **not** state whether simultaneous Hex processes safely mutate one `HEX_HOME`. So sharing a writable Hex cache across parallel builds is technically possible with BuildKit's default `shared` mode, but Hex's concurrent-writer safety is unverified by these sources. Conservative choice: give concurrent workers distinct Hex cache homes/cache IDs, or serialize access with BuildKit `sharing=locked`; treat this as risk control, not a documented Hex requirement. BuildKit cache mounts are disposable build caches, not durable storage.

For running containers, Docker volumes persist and can be shared between containers; bind mounts are read-write by default and changes flow back to the host. These runtime mounts do not inherit BuildKit's `sharing=locked` behavior. [Docker container mounts](https://docs.docker.com/engine/containers/run/#filesystem-mounts)

Because `HEX_HOME` includes configuration as well as cache, sharing the whole home also shares Hex configuration. For build-time credentials, Docker documents secret mounts as the mechanism to provide secrets without baking them into the image or build cache. [Hex config](https://hex.hexdocs.pm/Mix.Tasks.Hex.Config.html) · [Docker secret mounts](https://docs.docker.com/reference/dockerfile/#run---mounttypesecret)
