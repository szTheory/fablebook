## Summary

Both contract files pass locally (53 tests, Elixir 1.20.4 / OTP 29.1.1). I tested the findings below empirically:

- **Ban sets.** I compiled candidate modules and scanned them with the exact `@atom_tier`/`@mfa_tier` matching logic from `banned_calls_test.exs`.

`hex_publish_test.exs` misses several one-line regressions that disable the gates it claims to guard.

Already-tracked items are not repeated: T-01.1-06, T-01.1-07, Q35, Q37 and the WR-05 follow-up. CR-01 is not T-01.1-07: in every form it lists, the module and function are compile-time literals.

## Critical Issues

### CR-01: Literal MFA dispatch passes the BEAM guard whenever the call is not a direct remote call

**File:** `test/contract/banned_calls_test.exs:266-270` (`hits/1`), `test/support/beam_walker.ex:21` (`mfas: imports`), `credo/checks/banned_calls.ex:14-16`
**Issue:** `@mfa_tier` is matched only against the `:imports` chunk. A call shows up there only when the compiler emits it as a direct remote call. If the module and function are literals but the argument list is not a literal list, or the call goes through a dispatcher, the import becomes `erlang:apply/3`, `erlang:spawn/3`, `erpc:call/4`, `Task:async/3` or `erlang:make_fun/3`. Every MFA-tier name that is not also in `@atom_tier` then passes.

These were compiled and scanned with the test's own tiers, and all of them pass the guard:

```elixir
apply(:erlang, :load_module, args)               # imports: erlang:apply/3
apply(:file, :script, args)
apply(Module, :concat, args)                     # atom creation from input (T-01.1-01 marked closed)
apply(:erlang, :load_module, [m | rest])
Function.capture(:file, :script, n).(p)          # imports: erlang:make_fun/3
spawn(:file, :script, [p])
:erpc.call(node(), :file, :script, [p])
:rpc.call(node(), :erlang, :load_module, [m, b])
Task.async(Module, :concat, [x])
```

The same applies to `:compile.forms`, `Kernel.ParallelCompiler.require`, `:elixir_module.compile`, `:code.load_binary`, `:epp`, `:xmerl_scan` and `EEx` used through any of these forms.

In every case the module and function are compile-time literals, so this is not the accepted runtime-computed residual (T-01.1-07). The Credo moduledoc says the BEAM guard "is the gate for every literal or compiled form", which is false. The `default_arg_to_atom` fixture passes only because `:to_atom` happens to be in the atom tier. No fixture covers an MFA-tier-only name through `apply` with a variable list.

**Fix:** match MFA patterns against literal atom pairs in the abstract code, not only against imports. The walker change is Q35 territory. Make it in a PR that does not touch `lib/`.

```elixir
# beam_walker.ex: also return every adjacent literal {module, function} pair
pairs: pairs(forms, MapSet.new())

defp pairs([{:atom, _, m}, {:atom, _, f} = next | rest], acc),
  do: pairs([next | rest], MapSet.put(acc, {m, f}))
defp pairs(term, acc) when is_list(term), do: Enum.reduce(term, acc, &pairs/2)
defp pairs(term, acc) when is_tuple(term), do: pairs(Tuple.to_list(term), acc)
defp pairs(_term, acc), do: acc

# banned_calls_test.exs hits/1
pair_hits =
  for {m, f} <- scan.pairs,
      Enum.any?(@mfa_tier, fn {pm, pf, _} -> pm == m and pf in [:_, f] end),
      do: {:mfa, {m, f, :_}}
```

This catches `{:remote, _, {:atom,_,M}, {:atom,_,F}}`, `apply/3`, `spawn/3`, `erpc`/`rpc`, `Task.async/3`, `make_fun/3` and `{M, F, A}` tuples. For whole-module entries (`{EEx, :_, :_}`, `{:compile, :_, :_}`, `{:epp, :_, :_}` and so on), also flag the bare module atom wherever it appears in `scan.atoms`.

- Add fixtures for `apply(:erlang, :load_module, args)` and `Task.async(Module, :concat, [x])`.
- Correct the Credo moduledoc claim.

### CR-03: The main-only check validates the tag name, not the commit that is built, published and smoke-tested

**File:** `.github/workflows/hex-publish.yml:39-43, 53, 115-118, 128-130, 146-149`
**Issue:** the ancestry check resolves `"$TAG"` itself, separately from the checkout. Two ways to defeat it, both open to the same actor T-01.1-09 models (someone with write access):

1. **Branch/tag ambiguity.** `actions/checkout` resolves an unqualified `ref:` as a branch first (`origin/<ref>`) and only then as a tag. `git rev-parse` resolves `refs/tags/` before `refs/heads/`. Reproduced locally:
   - Tag `v1.0.0` is on main. A branch `v1.0.0` holds an off-main commit, checked out the way actions/checkout does it.
   - `git merge-base --is-ancestor v1.0.0 origin/main` exits 0 ("warning: refname 'v1.0.0' is ambiguous").
   - `git merge-base --is-ancestor HEAD origin/main` exits 1.

   The build then tests, builds and smoke-tests the off-main tree. The version check passes if the branch sets `version` to match.
2. **Re-resolution after the check.** The `publish` and `smoke` jobs check out `ref: ${{ inputs.tag }}` again. In the `todo=package` path, `mix hex.publish --yes` builds a fresh tarball from that second checkout and never compares it to `$SHA256`.
   - A tag force-moved between `build` and `publish` gets published.
   - The `hex-production` approval wait widens that window.
   - Smoke only notices afterwards, through its checksum, once the package is already on hex.pm.

   The `todo=docs` path also publishes docs from the re-resolved tree.

`hex_publish_test.exs` cannot see either problem. Its fixture repo never models the checkout. Mutation 1 even treats `HEAD` as the wrong operand, but `HEAD` is the commit that actually gets built.

**Fix:** resolve the tag once, to a commit, and use that commit everywhere.

```yaml
      - uses: actions/checkout@...
        with:
          ref: refs/tags/${{ inputs.tag }}
      ...
      - id: tag
        run: |
          [[ "$TAG" =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]]
          sha="$(git rev-parse "refs/tags/$TAG^{commit}")"
          test "$(git rev-parse HEAD)" = "$sha"
          if ! git merge-base --is-ancestor "$sha" origin/main; then
            echo "::error::$TAG is not on main"
            exit 1
          fi
          ...
          echo "sha=$sha" >> "$GITHUB_OUTPUT"
```

- Expose `sha` as a job output.
- Check out `ref: ${{ needs.build.outputs.sha }}` in `publish` and `smoke`.
- In `publish`, before `mix hex.publish --yes`, rebuild and require `sha256sum` to equal `$SHA256`.
- Per ADR 0021, the contract test change goes in its own PR first. That change models the checkout, flips mutation 1's expectation, and adds a same-named-branch case.

## Warnings

### WR-01: The contract test misses a step-level `if:` that skips the ancestry or checksum gate

**File:** `test/contract/hex_publish_test.exs:146-163, 182-189`
**Issue:** `order_violations` only checks the step order, `continue-on-error` and `shell:`. `gate_violations` checks that steps *after* `hex` carry the gate, but never checks `tag` or `hex` themselves. Each of these mutations of `hex-publish.yml` leaves the test file at 25/25 passing:

- `- id: tag` plus `if: false`. The ancestry check is skipped and `V` becomes empty. The publish job then probes `releases/` and can take the `todo=package` path.
- `- id: hex` plus `if: false`. The skipped step leaves `todo` empty. The `!= 'none'` gate then fails open and publishes the package with no checksum comparison.
- `if: false` on the `test -n "$HEX_API_KEY"` step.

**Fix:**
- Require that the `tag`, `hex` and key-check steps carry no `if:` key, and that build-job steps carry none at all.
- Make the gate fail closed:

```yaml
- if: steps.hex.outputs.todo == 'package' || steps.hex.outputs.todo == 'docs'
```

- Pin that exact string in `@gate`, and add mutations for both `if: false` cases.

### WR-02: Secret-scope check misses job-level `env:` placed after `steps:`

**File:** `test/contract/hex_publish_test.exs:207-229`
**Issue:** the job-level scan reads only `Enum.take_while(body, &(&1 != "    steps:"))`. `steps/1` stops at the first line that is not indented six spaces. A job-level `env:` written after the step list falls in neither. Adding this before `publish:` still passes 25/25:

```yaml
    env:
      HEX_API_KEY: ${{ secrets.HEX_API_KEY }}
```

That hands the key to every build step, including tag-controlled `mix test`, setup and `bin/smoke_consumer`. This is the T-01.1-12 exposure the test exists to block. The secret arrives through `workflow_call`, so `environment:` does not restrict it.

**Fix:** scan every job line that is not a step line, not just the lines before `steps:`:

```elixir
step_lines = body |> steps() |> List.flatten() |> MapSet.new()
for {id, body} <- jobs, line <- body, line not in step_lines, secret?(line), do: {:secret_scope, id, line}
```

Add the trailing-env mutation.

### WR-03: The line-based step parser truncates silently, which makes the cache check vacuous

**File:** `test/contract/hex_publish_test.exs:342-350, 242-248`
**Issue:** `steps/1` uses `take_while(&(&1 == "" or String.starts_with?(&1, "      ")))`. A valid YAML comment indented four spaces (`    # lanes`) between steps ends the step list. Every later step disappears from `cache_violations`, `holders` and `find_step`.

Verified: insert `    # lanes` before the smoke job's setup step and flip its `cache: 'false'` to `'true'`. The suite still passes 25/25.

`find_step` returning `[]` fails closed for the behavioural checks. `cache_violations` and the job-level secret scan pass vacuously.

**Fix:**
- Skip comment lines inside `steps/1`: `&1 == "" or &1 =~ ~r/\A\s*#/ or String.starts_with?(&1, "      ")`.
- Assert each job's parsed step count against a pinned count per job, so a truncated parse fails.

### WR-04: The mix.exs scan ignores the whole MFA tier

**File:** `test/contract/banned_calls_test.exs:221-239`
**Issue:** `mix_exs_hits/1` only checks `@atom_tier` names. The eval and load entries live in `@mfa_tier`, so all of these pass `mix.exs names no banned call or module`:

- `:file.eval("x")`, `:file.script(p)`, `Code.load_file(p)`
- `Kernel.ParallelCompiler.require([p])`, `:erlang.load_module(m, b)`
- `Module.concat([x])`, `:qlc.string_to_handle(s)`

T-01.1-04 ("eval or atom creation in mix.exs") is marked closed on the strength of this scan.

**Fix:** also scan for qualified MFA-tier names.

```elixir
mfa_names =
  for {m, f, _} <- @mfa_tier do
    mod = m |> inspect() |> String.replace_prefix("Elixir.", "")
    if f == :_, do: mod, else: "#{mod}.#{f}"
  end
```

Match each name with the same `(?<!\w)…(?![\w!?])` regex. Add positive samples for `:file.eval(x)` and `Module.concat(x)`.

## Info

### IN-01: The test harness shell differs from the runner's

**File:** `test/contract/hex_publish_test.exs:259-271`
**Issue:**
- `run/4` executes step bodies with `bash -e`. GitHub runs `bash --noprofile --norc -eo pipefail`, so a pipeline added to a tested step behaves differently under test.
- `run/4` also does not clear `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE`, which `git!/2` does through `@git_env`. Run under a git hook or `git rebase --exec`, the tag script's `git merge-base` would query the outer repository.

**Fix:** use `System.cmd("bash", ["--noprofile", "--norc", "-eo", "pipefail", "step.sh"], env: @git_env ++ [...])`.

### IN-02: The job graph and checkout refs are unguarded

**File:** `test/contract/hex_publish_test.exs` (whole file); `.github/workflows/hex-publish.yml:164-165`

None of this is claimed by the current tests. However, CR-03's fix depends on the checkout refs, and the draft-until-smoke promise in the smoke failure message depends on `finalize` needing `smoke`.
