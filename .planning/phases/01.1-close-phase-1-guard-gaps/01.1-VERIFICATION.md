### Gaps Summary

There are two root causes. Both fall short of the goal's own wording; the success criteria as worded are met.

**A. The BEAM guard sees only direct remote calls (truths 5, 6, 7).** `@mfa_tier` is compared only against the imports chunk. A literal `{module, function}` reached through `apply/3` with a non-literal list, `spawn/3`, `:erpc`/`:rpc`, `Task.async/3` or a variable-arity `Function.capture/3` imports only the dispatcher, so it passes. The to_atom family is safe only because the atom tier matches those names anywhere. `Module.concat` and every load or eval entry are not. Separately, the enumerated list misses direct public eval, compile-and-load and native-load APIs, and `:qlc.string_to_handle` evaluates input and creates atoms. The fix lives in `test/support/beam_walker.ex` (pair matching) and `@mfa_tier` (new entries). The walker is outside the D-21 table (Q35 pending), so it ships in its own PR that touches no `lib/`, `.github/` or `mix.exs`. Then correct the Credo explanation.

**B. The main-only check verifies a name, not the published commit (truth 8).** A branch with the same name as the tag wins at checkout, while git resolves `$TAG` to the tag. Publish also re-resolves the ref and does not compare checksums before uploading. Per ADR 0021, `hex_publish_test.exs` is changed first (model the checkout, a same-named-branch case, flip mutation 1). Then a `.github/` PR pins `refs/tags/<tag>`, carries the resolved SHA through all jobs and verifies the checksum before `mix hex.publish`.

**No deferral applies.** Phase 5's SC4 proves zero new atoms through `handle_params` on URL and control input. That is a runtime property over specific paths, not a static ban over every `lib/` module's literal dispatch. No later phase owns the hex-publish ref handling. Q37 (the `v*` deployment policy) is a different issue.

`01.1-SECURITY.md` already reopens T-01.1-01, -02, -03 and -09 for the same reasons (`threats_open: 4`). This report agrees with it.
