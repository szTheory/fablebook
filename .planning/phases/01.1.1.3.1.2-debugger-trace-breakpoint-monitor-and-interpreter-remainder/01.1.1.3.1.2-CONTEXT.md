<decisions>
## Implementation Decisions

### Coverage granularity
- Inventory all functions and exports in the currently assigned debugger remainder on both supported lanes. Use exact function and source-branch dispositions for risky routes; do not blanket-ban benign modules or stop at the export list.
- Use the installed BEAM graph to find callers and routes, then review source for private branches and unresolved dynamic `apply` / `spawn` paths. A graph result alone does not establish that a dynamic route is absent.

### Trace and breakpoint route semantics
- Treat configured auto-attach and conditional-breakpoint callbacks as executable code paths, not inert settings. Trace the setter, stored value, event gate, and dispatch branch without invoking the callback.
- Preserve the previous phase’s branch and root ownership exactly. In particular, do not move the selected saved-settings roots or the conditional callback body/outcomes from Phase 01.1.1.3.1.1 into this remainder.

### Evidence standard
- Pair exact-lane source identity and branch citations with installed BEAM function/export inventories, graph-derived routes, current ownership receipts, and compile-only static guard probes where the guard changes.
- Report what this proves as static coverage only. Do not add live debugger integration tests or infer runtime safety from the tests.
- Keep the floor at Elixir 1.18.5 / OTP 27.3.4.9 and the latest lane at Elixir 1.20.4 / OTP 29.1.2. Pinned lane source controls exact behavior when a general OTP manual differs.

### the agent's Discretion
- The owner asked to consider all relevant areas, fan out across relevant technical perspectives, and auto-follow a coherent recommendation. All three areas above were selected and the recommendations were adopted. Relevant perspectives are security, Elixir/OTP semantics, compatibility, maintainer DX, and CI/SRE. UI, accessibility, graphics, and brand-book decisions do not apply to this internal security phase.
- Keep the existing dependency budget. Prefer the repository’s current tools and a small local helper over a new dependency; a new dependency requires a written ADR.
- Use the existing ownership/audit record style and existing test infrastructure. Do not create a parallel authority or a new audit platform.

</decisions>

<specifics>
## Specific Ideas

OTP’s `int:auto_attach` accepts a callback MFA and invokes it via `spawn/3` for configured events; conditional breakpoint checks call the configured function with interpreter bindings. These are executable routes that should be traced in source and covered statically, without running the callbacks. The independent reviewers converged on precise function/branch dispositions over module-wide bans, and paired source/BEAM/compile-only evidence over live debugger tests.

</specifics>
