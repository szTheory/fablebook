# Verification policy

Owner direction: INT-20261029-08 and [INT-20261120-13](intent/sources/2026-11-20-13-automated-verification-and-resource-hygiene.md). Applies to every GSD discussion, plan, execution, review, verification and resume. The target is zero human UAT wherever the behavior can be checked automatically.

1. Map each acceptance criterion to existing executable evidence before adding work. Use the cheapest boundary that proves observable behavior: unit/property, integration, seam, consumer smoke, then browser E2E (ADR 0014).
2. Run checks autonomously inside the requested step. Replace reproducible manual instructions with durable tests. Test the real script or application at its boundary, including negative controls and failure paths; mock external writes so verification cannot publish or message by accident.
3. Put checks in existing CI lanes when they protect recurring behavior. Keep one-off historical reads in the phase evidence; preserve the three-workflow cap, latency budgets and contract-test separation (ADR 0017, ADR 0021).
4. Record test commands, results, tested revision, relevant file paths and CI run links in the phase UAT/verification files. Use `source: automated` for automated passes. Distinguish local checks from CI. Historical evidence stays historical; rerun checks when guarded code, dependencies or environment changed, a regression is reported, or evidence was incomplete.
5. Reuse recorded approvals and resolved findings. Before opening a gap, reconcile it against executed plans, merged PRs and explicit roadmap transfers. A previously approved decision needs no repeat sign-off without a material change. Record why remaining checks are unnecessary, unavailable or owned elsewhere.
6. Time-gated evidence belongs to scheduled automation with an explicit owner, command and observation point. Missing history remains `not-run`; it is not a human test or a pass. Escalate only if the automation cannot observe or enforce the requirement.
7. Hand off only irreducible human judgment (such as accepting a visual baseline or the owner's preference), inaccessible authority, or a real unresolved product decision. State the exact residual and why tools cannot resolve it. Keep existing gates, visual-baseline rules and honesty requirements intact.
8. Whenever CI is in scope or a run finishes, inspect the measured critical path and current history for recurring, low-risk iteration-time improvements (queue time, duplicated work, avoidable serialization, cache misses and slow setup/test steps). Preserve all quality gates, required coverage and thresholds. Change CI only when the evidence shows a repeatable gain with no loss of coverage; otherwise record that no safe low-hanging improvement was found. Do not trigger extra runs only to create a receipt; batch CI evidence with substantive changes.
9. Treat CI duration budgets as feedback-time objectives unless the owner has explicitly approved them as release gates. A timing-only overage stays visible in reporting and a performance issue; it does not become a quality-regression release blocker or prevent phase closure. Preserve correctness, security, compatibility, required-check and release-smoke gates.
10. For serial GSD work, stay in the current checkout. `--ws` selects a logical workstream; it does not create filesystem isolation. Use another worktree only for actual parallel work or a concrete isolation need. Keep assistant/session context limits separate from owner-approved project source, effort, reserve and safety budgets; do not stop authorized work on an extra cumulative assistant-side ceiling or ask for repeated small budget increases. If a project budget really needs revision, measure the complete remaining authorized work once and propose one viable bounded path.

INT-20261029-05 still applies: finish the requested GSD step and show its next command; the owner chooses when to advance. Autonomous verification does not enable workflow auto-advance.

INT-20261029-09: End every GSD response with a concrete next command and its purpose, even when a phase is partial or blocked. State separately whether a PR can merge, whether the phase can close, and what independent work can proceed. A pending scheduled observation does not itself block a green, scoped automation PR or planning work whose own dependencies are verified. Batch bookkeeping with substantive pushes; link final CI evidence from the PR instead of creating a receipt-only commit that triggers another identical run.

## Automation-first verification defaults — INT-20261118-01

Before creating or continuing UAT, map every checkpoint to the current phase's stated deliverable and its existing receipts. Separate current-phase acceptance from a later product decision or authorization. When an already-approved decision covers the current bounded result, do not ask the owner to repeat it. Convert machine-checkable expectations into deterministic local checks with negative controls where useful, mark them source: automated, and keep genuinely irreducible owner judgment or authority as the only human handoff. A future decision that is not needed for the current deliverable remains a recorded stop; it does not become a UAT blocker.

Use the cheapest useful evidence first: diff and schema checks, hashes and provenance bindings, then a focused test or seam, then integration/smoke checks, then the full required suites. Stop at the first failure and fix its cause before proceeding. Reuse a passing receipt only when its tested revision, dependencies, environment, and guarded inputs are unchanged; otherwise rerun only the checks invalidated by the change. One-off or throwaway checks are welcome when they answer a real question, but do not add them to CI unless they protect recurring behavior.

For serial work, stay in the current checkout. The --ws flag selects a logical GSD workstream, not a filesystem checkout. Use another worktree only for real parallel work or a concrete isolation/preservation need; preserve dirty recovery checkouts and follow their recorded transfer instructions.

This policy applies to verification, review, CI, and release/CD. After each completed CI or release run, use the measured critical path and comparable history to look for safe reductions in queue time, repeated setup/work, serialization, retries, or output volume. Make recurring changes only when they improve feedback time without reducing coverage, security, or release confidence; record when the evidence supports no change. See CI-PERFORMANCE.md.

## Local action runs and Docker resources — INT-20261120-13

- Use `act` for relevant GitHub Actions when the current local runner can execute the workflow faithfully. It supplements hosted receipts and does not replace required hosted CI. Reuse a known local failure assessment; do not repeat a blocked `act` attempt unless its cause or environment has changed. Fablebook's last recorded `act` attempt could not run tests because of an ARM64/amd64 setup-beam mismatch; hosted CI remains the useful evidence unless that setup changes (see CI-PERFORMANCE.md).
- Use Docker only when it provides a concrete test or environment benefit. Give task-created containers, images, networks, and volumes an identifiable `fablebook-<milestone-or-task>-<purpose>` name/label. Record ownership and clean up only resources created for that task. Do not run broad prune commands or delete ambiguously owned resources.
- Evaluate useful local throwaway checks without automatically promoting them to CI. Add recurring CI only when it protects repeated behavior; preserve all existing delivery, security, compatibility, and visual-baseline gates.

## CI efficiency review

For the 2026-11-06 Phase 1 review, current read-only Actions API data was evaluated with the existing `ci-health` sample eligibility and percentile rules. Its latest published sample is stale because the Nov 6 scheduled run skipped `ci-health`; a fresh calculation found p50 489 s and p95 783 s over 50 first-attempt, non-release PR runs in the latest seven-day window. The Nov 6 scheduled run's core and floor jobs overlapped; `mix ci` took 6m42s and the floor test command took 8m51s. Dependency/build caches are already wired. No safe step removal or quality-preserving quick win is established by this evidence. Keep 420/600 seconds as visible performance objectives, but timing-only overages must move to non-blocking `ci-performance` tracking under INT-20261106-01; use per-step and queue evidence before proposing a targeted optimization.
