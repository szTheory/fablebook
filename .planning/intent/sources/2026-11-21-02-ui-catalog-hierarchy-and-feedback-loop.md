# Owner direction: make the UI catalog hierarchy and language clear

**Date:** 2026-11-21
**Provenance:** Direct owner messages and reaction to the local Phase 8 screens in the active Fablebook planning conversation.

> “i think we need some kind of way to flip between idk what we call this but all the parts of our UI catalog and a sidebar seems pretty intuitive for that unless we have some specific great version to reinvent the wheel seems like a good default way to present it so you can look through the catalog pick one (which is in a sidebar) and then the main panel shows the actual UI in question”
>
> “maybe u should apply that from a content hierarhcy/info hierarchy layout perspective and then also apply impeccable UI skill to it too to de-slop it”
>
> “also like make sure u are clarifying/disambiguating/curating domain language like what is a \"book\" what is a \"catalog\" do we call it a \"UI catalog\"”
>
> “we need to make all these terms clear take advantage of any learning activity / feedback as a opportunityt o get dividends by adjusting gameplan remember the kind of feedback etc..."

The owner also identified the specific ambiguity after seeing the local UI:

> “but i guess its confusing we are calling the top level list of books a \"catalog\" but i thought each individual \"book\" was like a \"catalog\".”

Apply the product language already settled in [INT-20261111-06](2026-11-11-06-fablebook-brand-intake.md): Fablebook is “a UI catalog for Phoenix LiveView”; a Book is one adopter-defined catalog. In the UI, “Books” is the collection label; do not call the top-level Books collection “the catalog.” Keep Book, Story, Scenario and Canvas as distinct terms.

For the active one-Book development surface, use a familiar persistent sidebar to browse Book → Story → Scenario and render the selected Scenario through the real Canvas in the main panel. Opening the local UI should make the first screen inspectable without an extra card-index step. Keep the Book content illustrative and preserve all Phase 8 limits.

For future UI work, record reusable owner feedback with this provenance, map the user flow and job to be done, check labels against `GLOSSARY.md` and the pinned brand guidance, and run an adversarial review against the accumulated feedback before presenting a screen. Add only reusable lessons to the feedback ledger; keep one-off corrections in their intent source.
