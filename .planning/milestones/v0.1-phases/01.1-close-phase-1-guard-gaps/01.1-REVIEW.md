#### Critical Issues

##### CR-04: A user-defined `__info__/N` hides literal dispatch from the pair and literal checks

**File:** `test/support/beam_walker.ex:37-38`
**Issue:** `function_code/1` drops every `{:function, _, :__info__, _, _}` form, whatever its arity. Plan 01.1-03 justifies the skip with "Elixir refuses a user-defined `__info__/1` … so skipping it hides no user code". The 01.1-03 summary says the same: "Compiler-generated `__info__/1` is skipped". But Elixir only reserves arity 1. A lib/ module can define `def __info__(m, args)` or `def __info__()`, and the walker then never scans its body for pairs or literals.

The imports chunk holds only `erlang:apply/3`. Credo's `@names` has no `load_module` or `concat`. So both static layers pass the exact CR-01 shape this phase set out to close.

I probed this through the test's own `hits/1`:

```elixir
defmodule Fablebook.Probe.InfoTwo do
  def __info__(m, args), do: apply(:erlang, :load_module, [m | args])
  def run(m, args), do: __info__(m, args)
end
# hits=[]  imports=[{:erlang, :apply, 3}, {:erlang, :get_module_info, 1}, {:erlang, :get_module_info, 2}]
```

On the floor lane (Elixir 1.18.4 / OTP 27.3.4.15) the same module compiles, and its debug info lists both `{:__info__, 1}` and `{:__info__, 2}`. So the bypass holds on both lanes. `apply(Module, :concat, args)` hides the same way inside a user `__info__/0` or `__info__/2`, which is the T-01.1-26 atom-creation path.

**Fix:** skip only the generated arity, and add a fixture so the test proves it:

```elixir
defp function_code(forms),
  do: for({:function, _, name, arity, _} = form <- forms, {name, arity} != {:__info__, 1}, do: form)
```

```elixir
# test/fixtures/guards/info_arity_two.ex
defmodule Fablebook.GuardFixture.InfoArityTwo do
  def __info__(module, args), do: apply(:erlang, :load_module, [module | args])
end
```

Add `{"info_arity_two.ex", {:mfa, {:erlang, :load_module, :_}}}` to `@fixtures` and add the file to `@beam_only_fixtures`.

I tested the arity-specific filter in the scratch copy. The full `banned_calls_test.exs`, plus the probe, gave `40 passed`: the lib/ scan stays clean, the strictness rows are unchanged, and `InfoTwo` now hits `{:mfa, {:erlang, :load_module, :_}}`. The change touches the walker, a fixture and the contract test, and no `lib/`, `.github/` or `mix.exs` path.

#### Warnings

##### WR-06: The step harness runs a stricter shell than the runner, so a `| cat` makes the main-only check fail open undetected

**File:** `test/contract/hex_publish_test.exs:446-451` (`run/4`); `.github/workflows/hex-publish.yml:54`
**Issue:** `run/4` executes step bodies with `bash --noprofile --norc -eo pipefail`. The workflow's steps declare no `shell:`, and `order_violations/1` (`:342-346`) forbids one. So on GitHub every step runs as `bash -e {0}`, without `pipefail`. The CI log of run https://github.com/szTheory/fablebook/actions/runs/40899871001 shows `shell: /usr/bin/bash -e {0}` for plain `run:` steps.

Any gate whose verdict depends on a pipeline's exit status is therefore judged under the wrong semantics. Take this mutation:

```yaml
if ! git merge-base --is-ancestor "$sha" origin/main | cat; then
```

- Under `pipefail` (the harness), the pipeline fails, so the error branch runs and every gate case matches.
- Under `bash -e` (the runner), the pipeline's status is `cat`'s `0`, so an off-main tag passes the check.

The mutated workflow left the five behavioural tests at `5 passed`. A standalone script confirmed the divergence: `bash -e` printed `sha=passed` with exit 0, and `bash --noprofile --norc -eo pipefail` printed the error with exit 1.

**Fix:** run step bodies the way the runner does. Then add the pipe mutation to `@mutations`, all in one contract-test-only PR:

```elixir
System.cmd("bash", ~w(-e step.sh), cd: cwd, env: @git_env ++ [...], stderr_to_stdout: true)
```

```elixir
{:ancestry, "origin/main; then", "origin/main | cat; then"}
```

I tested this in the scratch copy. With `bash -e`, the unmutated suite gives `44 passed`, and the pipe mutation fires `{:ancestry, "tag only on local main", …}` and `{:ancestry, "no origin/main", :built_commit_off_main}`.

The other route is to set `defaults: run: shell: bash` in the workflow. That needs the `shell:` ban changed first, in its own PR (ADR 0021).

##### WR-07: Secret-scope check is blind to top-level keys placed after `jobs:`

**File:** `test/contract/hex_publish_test.exs:393-415`, `:526-535`
**Issue:** `secret_violations/1` reads three places, each with a different scan:
- the preamble: lines before `jobs:`, checked against `@declared`;
- job lines outside the step lists;
- step holders.

`jobs/1` stops at the first top-level line after the job block. So a workflow-level `env:` moved after the jobs is not read by any of the three. I tested this mutation: remove the top-level `env:` at `hex-publish.yml:25-27`, then append the block below to the end of the file. The five behavioural tests stayed at `5 passed`.

The key arrives through `workflow_call` as a repository secret (`release-please.yml:38-39`), so the `hex-production` environment does not limit it. Keep the holder check, which still says which steps hold the key. Add the trailing top-level `env:` mutation.

##### WR-08: The draft-until-smoke promise can be broken with an `if:` on `finalize` or on a smoke step

**File:** `test/contract/hex_publish_test.exs:213-228`, `:327-341`; `.github/workflows/hex-publish.yml:180-181`, `:189-199`
**Issue:**
- **What IN-02's fix pinned.** It pinned `finalize: needs: smoke`.
- **Where `if:` is checked.** The test checks a job-level `if:` only on `publish` (`key(publish, "if")`, `:339`). It checks step-level `if:` only on build steps, `hex` and the key check (`:214-218`).
- **What breaks the promise.** Each of these mutations left the five behavioural tests at `5 passed`, and each un-drafts the release without a passing smoke:
  - `    needs: smoke` followed by `    if: always()` on `finalize`. `finalize` then runs after a failed smoke and un-drafts the release.
  - `if: false` on the smoke step `run: bin/smoke_consumer --hex "$V" --checksum "$SHA256"`. Smoke then "passes" without running.
- **Why it matters.** The smoke failure message promises "Tag $TAG stays a draft" (`hex-publish.yml:187`).

**Fix:**
- Require no job-level `if:` on `build`, `smoke` and `finalize`, as `publish` already is.
- Extend `step_if_violations/1` to every smoke step except the reporter.
- Pin the reporter's condition exactly:

```elixir
for id <- ~w(build smoke finalize), key(job(text, id), "if") != nil, do: {:step_if, id}
```

```elixir
smoke = job_steps(text, "smoke")
reporter = Enum.filter(smoke, &("if: failure()" in normalized(&1)))
check(length(reporter) == 1, {:step_if, :smoke_reporter}) ++
  for(step <- smoke -- reporter, Enum.any?(normalized(step), &String.starts_with?(&1, "if:")),
      do: {:step_if, action(step)})
```

##### WR-11: Module-body code reaches MFA-tier calls past both static layers

**File:** `test/support/beam_walker.ex:12,16,37-38` (only debug-info function forms are walked); `credo/checks/banned_calls.ex:14-45` (the explanation's list of misses omits it)
**Issue:** code in a `defmodule` body, including module-attribute expressions, runs at compile time and leaves nothing in the beam. Credo matches only `@names`, which has no MFA-tier function names. Two probes compiled as lib-style modules gave `hits=[]` and 0 Credo issues:

```elixir
defmodule Fablebook.Probe.BodyScript do
  @result apply(:file, :script, [System.get_env("FB_PROBE_PATH")])
  def run, do: @result
end

defmodule Fablebook.Probe.BodyConcat do
  @mod Module.concat([System.get_env("FB_PROBE_NAME", "ZzProbe")])
  def run, do: @mod
end
```

Compiled with `FB_PROBE_PATH` pointing at a file that contains `erlang:list_to_atom("zz_body_probe_atom").`, `BodyScript.run()` returned `{:ok, :zz_body_probe_atom}`. So the file was evaluated, and an atom created from its content, at compile time on the machine that builds the dependency. A direct call such as `@r :file.script(p)` is just as invisible.

The Credo explanation tells readers the BEAM guard "checks the compiled code of each lib/ module" and lists what it misses, without naming module bodies. I rate this a warning, not a blocker, because the inputs are the building machine's own environment and files, not request input. ADR 0004 still says "ever".

**Fix:** add a source-level MFA-tier check that covers module bodies. Credo already walks the whole source:
- flag `{{:., _, [mod, fun]}, _, _}` remote calls whose expanded module and function match a tier entry;
- flag adjacent literal module and function arguments, using the same rule as the walker.

Pin a strictness row for the module-body case, and add one sentence to the explanation's list of misses until that check lands. This is a `credo/` plus contract-test PR, with no `lib/` change.

### Critical Issues

#### CR-01: Literal MFA dispatch passes the BEAM guard whenever the call is not a direct remote call

**File:** `test/contract/banned_calls_test.exs:266-270` (`hits/1`), `test/support/beam_walker.ex:21` (`mfas: imports`), `credo/checks/banned_calls.ex:14-16`
**Issue:** `@mfa_tier` is matched only against the `:imports` chunk. A call shows up there only when the compiler emits it as a direct remote call. If the module and function are literals but the argument list is not a literal list, or the call goes through a dispatcher, the import becomes `erlang:apply/3`, `erlang:spawn/3`, `erpc:call/4`, `Task:async/3` or `erlang:make_fun/3`. Every MFA-tier name that is not also in `@atom_tier` then passes.

These were compiled and scanned with the test's own tiers, and all of them pass the guard:

```elixir
apply(:erlang, :load_module, args)               # imports: erlang:apply/3
apply(:file, :script, args)
apply(Module, :concat, args)                     # atom creation from input (T-01.1-01 marked closed)
apply(:erlang, :load_module, [m | rest])
Function.capture(:file, :script, n).(p)          # imports: erlang:make_fun/3
spawn(:file, :script, [p])
:erpc.call(node(), :file, :script, [p])
:rpc.call(node(), :erlang, :load_module, [m, b])
Task.async(Module, :concat, [x])
```

The same applies to `:compile.forms`, `Kernel.ParallelCompiler.require`, `:elixir_module.compile`, `:code.load_binary`, `:epp`, `:xmerl_scan` and `EEx` used through any of these forms.

In every case the module and function are compile-time literals, so this is not the accepted runtime-computed residual (T-01.1-07). The Credo moduledoc says the BEAM guard "is the gate for every literal or compiled form", which is false. The `default_arg_to_atom` fixture passes only because `:to_atom` happens to be in the atom tier. No fixture covers an MFA-tier-only name through `apply` with a variable list.

**Fix:** match MFA patterns against literal atom pairs in the abstract code, not only against imports. The walker change is Q35 territory. Make it in a PR that does not touch `lib/`.

```elixir
# beam_walker.ex: also return every adjacent literal {module, function} pair
pairs: pairs(forms, MapSet.new())

defp pairs([{:atom, _, m}, {:atom, _, f} = next | rest], acc),
  do: pairs([next | rest], MapSet.put(acc, {m, f}))
defp pairs(term, acc) when is_list(term), do: Enum.reduce(term, acc, &pairs/2)
defp pairs(term, acc) when is_tuple(term), do: pairs(Tuple.to_list(term), acc)
defp pairs(_term, acc), do: acc

# banned_calls_test.exs hits/1
pair_hits =
  for {m, f} <- scan.pairs,
      Enum.any?(@mfa_tier, fn {pm, pf, _} -> pm == m and pf in [:_, f] end),
      do: {:mfa, {m, f, :_}}
```

This catches `{:remote, _, {:atom,_,M}, {:atom,_,F}}`, `apply/3`, `spawn/3`, `erpc`/`rpc`, `Task.async/3`, `make_fun/3` and `{M, F, A}` tuples. For whole-module entries (`{EEx, :_, :_}`, `{:compile, :_, :_}`, `{:epp, :_, :_}` and so on), also flag the bare module atom wherever it appears in `scan.atoms`.

- Add fixtures for `apply(:erlang, :load_module, args)` and `Task.async(Module, :concat, [x])`.
- Correct the Credo moduledoc claim.

#### CR-03: The main-only check validates the tag name, not the commit that is built, published and smoke-tested

**File:** `.github/workflows/hex-publish.yml:39-43, 53, 115-118, 128-130, 146-149`
**Issue:** the ancestry check resolves `"$TAG"` itself, separately from the checkout. Two ways to defeat it, both open to the same actor T-01.1-09 models (someone with write access):

1. **Branch/tag ambiguity.** `actions/checkout` resolves an unqualified `ref:` as a branch first (`origin/<ref>`) and only then as a tag. `git rev-parse` resolves `refs/tags/` before `refs/heads/`. Reproduced locally:
   - Tag `v1.0.0` is on main. A branch `v1.0.0` holds an off-main commit, checked out the way actions/checkout does it.
   - `git merge-base --is-ancestor v1.0.0 origin/main` exits 0 ("warning: refname 'v1.0.0' is ambiguous").
   - `git merge-base --is-ancestor HEAD origin/main` exits 1.

   The build then tests, builds and smoke-tests the off-main tree. The version check passes if the branch sets `version` to match.
2. **Re-resolution after the check.** The `publish` and `smoke` jobs check out `ref: ${{ inputs.tag }}` again. In the `todo=package` path, `mix hex.publish --yes` builds a fresh tarball from that second checkout and never compares it to `$SHA256`.
   - A tag force-moved between `build` and `publish` gets published.
   - The `hex-production` approval wait widens that window.
   - Smoke only notices afterwards, through its checksum, once the package is already on hex.pm.

   The `todo=docs` path also publishes docs from the re-resolved tree.

`hex_publish_test.exs` cannot see either problem. Its fixture repo never models the checkout. Mutation 1 even treats `HEAD` as the wrong operand, but `HEAD` is the commit that actually gets built.

**Fix:** resolve the tag once, to a commit, and use that commit everywhere.

```yaml
      - uses: actions/checkout@...
        with:
          ref: refs/tags/${{ inputs.tag }}
      ...
      - id: tag
        run: |
          [[ "$TAG" =~ ^v[0-9]+\.[0-9]+\.[0-9]+$ ]]
          sha="$(git rev-parse "refs/tags/$TAG^{commit}")"
          test "$(git rev-parse HEAD)" = "$sha"
          if ! git merge-base --is-ancestor "$sha" origin/main; then
            echo "::error::$TAG is not on main"
            exit 1
          fi
          ...
          echo "sha=$sha" >> "$GITHUB_OUTPUT"
```

- Expose `sha` as a job output.
- Check out `ref: ${{ needs.build.outputs.sha }}` in `publish` and `smoke`.
- In `publish`, before `mix hex.publish --yes`, rebuild and require `sha256sum` to equal `$SHA256`.
- Per ADR 0021, the contract test change goes in its own PR first. That change models the checkout, flips mutation 1's expectation, and adds a same-named-branch case.

#### WR-01: The contract test misses a step-level `if:` that skips the ancestry or checksum gate

**File:** `test/contract/hex_publish_test.exs:146-163, 182-189`
**Issue:** `order_violations` only checks the step order, `continue-on-error` and `shell:`. `gate_violations` checks that steps *after* `hex` carry the gate, but never checks `tag` or `hex` themselves. Each of these mutations of `hex-publish.yml` leaves the test file at 25/25 passing:

- `- id: tag` plus `if: false`. The ancestry check is skipped and `V` becomes empty. The publish job then probes `releases/` and can take the `todo=package` path.
- `- id: hex` plus `if: false`. The skipped step leaves `todo` empty. The `!= 'none'` gate then fails open and publishes the package with no checksum comparison.
- `if: false` on the `test -n "$HEX_API_KEY"` step.

**Fix:**
- Require that the `tag`, `hex` and key-check steps carry no `if:` key, and that build-job steps carry none at all.
- Make the gate fail closed:

```yaml
- if: steps.hex.outputs.todo == 'package' || steps.hex.outputs.todo == 'docs'
```

- Pin that exact string in `@gate`, and add mutations for both `if: false` cases.

#### WR-02: Secret-scope check misses job-level `env:` placed after `steps:`

**File:** `test/contract/hex_publish_test.exs:207-229`
**Issue:** the job-level scan reads only `Enum.take_while(body, &(&1 != "    steps:"))`. `steps/1` stops at the first line that is not indented six spaces. A job-level `env:` written after the step list falls in neither. Adding this before `publish:` still passes 25/25:

```yaml
    env:
      HEX_API_KEY: ${{ secrets.HEX_API_KEY }}
```

That hands the key to every build step, including tag-controlled `mix test`, setup and `bin/smoke_consumer`. This is the T-01.1-12 exposure the test exists to block. The secret arrives through `workflow_call`, so `environment:` does not restrict it.

**Fix:** scan every job line that is not a step line, not just the lines before `steps:`:

```elixir
step_lines = body |> steps() |> List.flatten() |> MapSet.new()
for {id, body} <- jobs, line <- body, line not in step_lines, secret?(line), do: {:secret_scope, id, line}
```

Add the trailing-env mutation.

#### WR-03: The line-based step parser truncates silently, which makes the cache check vacuous

**File:** `test/contract/hex_publish_test.exs:342-350, 242-248`
**Issue:** `steps/1` uses `take_while(&(&1 == "" or String.starts_with?(&1, "      ")))`. A valid YAML comment indented four spaces (`    # lanes`) between steps ends the step list. Every later step disappears from `cache_violations`, `holders` and `find_step`.

Verified: insert `    # lanes` before the smoke job's setup step and flip its `cache: 'false'` to `'true'`. The suite still passes 25/25.

`find_step` returning `[]` fails closed for the behavioural checks. `cache_violations` and the job-level secret scan pass vacuously.

**Fix:**
- Skip comment lines inside `steps/1`: `&1 == "" or &1 =~ ~r/\A\s*#/ or String.starts_with?(&1, "      ")`.
- Assert each job's parsed step count against a pinned count per job, so a truncated parse fails.

#### WR-04: The mix.exs scan ignores the whole MFA tier

**File:** `test/contract/banned_calls_test.exs:221-239`

#### IN-01: The test harness shell differs from the runner's

**File:** `test/contract/hex_publish_test.exs:259-271`
**Issue:**

**Fix:** use `System.cmd("bash", ["--noprofile", "--norc", "-eo", "pipefail", "step.sh"], env: @git_env ++ [...])`.
