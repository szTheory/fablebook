## Architecture Patterns

### Creator fronts and branch provenance

In both archived exact lanes, `:file.consult/1` opens the supplied filename then reads through `consult_stream`; its existing trace reaches `:erl_scan` atom scanning. The official OTP description says `consult` reads Erlang terms, and `String.to_atom/1` documentation explicitly distinguishes conversion from creation. Treat “data parser” as no safety exemption: caller text containing atom tokens reaches atom interning. The existing `:file.path_consult/2` trace is already delivered and is only a reference point. [VERIFIED: `test/contract/tier_sweep_test.exs:1797-1879`; `test/fixtures/guards/exact_sources.tar.gz` (`core/kernel/src/file.erl:2272-2280,2900-2907`, floor counterparts); [OTP file docs](https://www.erlang.org/doc/apps/kernel/file.html); [Elixir String docs](https://elixir.hexdocs.pm/1.20.4/String.html#to_atom/1)]

Yecc's exact archived exports are `-export([compile/3, file/1, file/2, format_error/1]).` and `-export([yecc/2, yecc/3, yecc/4]).` in both lanes. `file/1` delegates to `/2`; `file/2` accepts caller `File` and delegates generation to `infile`; legacy `yecc/2..4` feed `Infile` to `file/2`. The output parser name is also caller-influenced through the outfile or `{parserfile, Parserfile}` option, so inspect input and output routes separately. Applicability/export claims must remain tied to these archive sources and be rechecked by runtime inventory on exact lanes during execution. [VERIFIED: `test/fixtures/guards/exact_sources.tar.gz` (`core/parsetools/src/yecc.erl:493-498,744-749,818-846,848-868`; floor equivalents); [OTP Yecc docs](https://www.erlang.org/doc/apps/parsetools/yecc.html)]

`Logger.Formatter.new/1` reads `options[:format]` and sends it to `compile/1`; the string branch calls `String.to_atom(code)`. A fixed `new/0` nil/default path is a useful negative control, but the `/1` caller-format branch remains independently unsafe. Logger config and explicit overrides have distinct provenance and both need branch dispositions; do not infer safety from “configuration” or startup callbacks. [VERIFIED: `test/fixtures/guards/exact_sources.tar.gz` (`core/logger/lib/logger/formatter.ex:169-175,439-459`; floor lines 152 and 402+); [Logger.Formatter docs](https://hexdocs.pm/logger/1.20.2/Logger.Formatter.html)]

- **Treating consult as “data only.”** Erlang term scanning can create atoms from textual atom tokens. Keep its caller-controlled file provenance and scanner sink in the source trace. [CITED: [OTP file docs](https://www.erlang.org/doc/apps/kernel/file.html); `test/contract/tier_sweep_test.exs:1834-1879`]
- **Missing Yecc compatibility exports.** Include `file/1,2` and `yecc/2,3,4` from source; `yecc/2..4` are compatibility wrappers into the file generator. Verify exact-lane exports during tests. [VERIFIED: `test/fixtures/guards/exact_sources.tar.gz` (`core/parsetools/src/yecc.erl:493-498,744-868`; floor equivalent)]
- **Collapsing Logger provenance.** Caller overrides, application configuration, explicit formatter and fixed defaults are separate branches. Never let a harmless default path exempt caller-controlled `new/1` or wrappers. [VERIFIED: exact-source archive paths listed above]
- **Calling a passing contract “complete.”** Ledger equality only preserves identities; representative samples only calibrate; neither closes unsampled semantic rows. Preserve Phase .4 ownership.
- **Pretending the sizing gate is measurable.** A new phase ID does not scope telemetry. If exact token accounting cannot be demonstrated, do not execute even if estimates look small.

### Token-meter research conclusion (RESOLVED for planning)

No reliable phase-local cumulative all-context model-token meter has been demonstrated in this managed conversation. That is the planning conclusion, **not** proof that such instrumentation could never be provided. Available documented surfaces have different scope:

- Codex `/status` describes the active chat/session, including current context usage and limits; it does not establish a GSD-phase baseline across chats or delegated contexts. [Official developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli).
- Desktop chat-level usage estimates the main conversation. Delegated subagents/separate tasks, background work and delayed or unavailable records may be omitted. These totals cannot demonstrate complete delegated coverage or phase-local headroom. [Official Work/Codex usage caveats](https://help.openai.com/en/articles/20001478-reviewing-work-and-codex-usage-and-using-personal-analytics-in-chatgpt-desktop).
- The organization Usage API groups time buckets by project, user, API key, model, batch, service tier and API source. It offers no GSD phase/thread grouping. There is no demonstrated mapping from those buckets to all work in this managed conversation. [Official organization completions usage reference](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/completions).
- Responses exposes token usage on an individual API response. No response identifiers or complete response-to-phase/context mapping for this managed Codex conversation have been supplied. Per-response usage is therefore not an available phase meter here. [Official response usage reference](https://developers.openai.com/api/reference/resources/responses/methods/retrieve).

The conclusion follows from documented scope plus the absence of a demonstrated baseline/probe in this environment.
