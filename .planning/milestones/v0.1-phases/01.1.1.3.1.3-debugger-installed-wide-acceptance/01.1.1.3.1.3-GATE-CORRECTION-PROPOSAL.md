# Proposal: separate validation delivery from phase completion

## Decision

For this phase only, publish a draft validation PR when the only remaining high findings are T-03 (exact-head CI evidence) and T-04 (post-merge identity evidence), and no high implementation finding remains. Keep the normal security threshold and ordinary ship gate unchanged.

The owner approved this narrow procedure. It allows collecting evidence; it does not close findings or mark the phase complete.

## Required stages

| Stage | Required evidence | Result |
|---|---|---|
| Publish draft PR | Confirm T-03/T-04 are the only open high items and there is no unresolved high implementation finding. Keep `threats_open: 2`. | Start exact-head CI; keep the PR draft. |
| Allow merge | The same PR head has green `core`, `floor`, `dialyzer`, `security`, and `ci-gate` checks. Core and floor aggregate markers match the phase source, owners, receipts, and jobs. | Close T-03 and update the count to `1`; merge that same head. T-04 remains open. |
| Complete phase | Independently verify PR head, CI run and jobs, merge SHA, and that main contains the merge. | Close T-04, update the count to `0`, and then complete this phase. |

Any additional high finding, unrelated code scope, failed check, or identity mismatch stops delivery. Do not lower `security_block_on`, disable security enforcement, or apply this exception to other phases. The regular `$gsd-ship` path remains fail-closed.

## Why this correction is needed

- Security enforcement is enabled with `security_block_on: high` in `.planning/config.json`.
- The GSD security-auditor contract counts open threats at or above that severity. The normal ship gate requires `threats_open: 0`.
- This phase has two high delivery findings: T-03 needs the PR's exact-head CI run; T-04 needs the completed merge identity. Those facts cannot both be observed before opening the PR.
- Keeping the normal gate unchanged while requiring a draft-only evidence stage allows those observations without declaring either finding mitigated early.

## Alternatives considered

- **Lower `security_block_on` or disable enforcement.** Rejected because it weakens unrelated security decisions.
- **Close T-03 or T-04 before obtaining its evidence.** Rejected because that would make the security report inaccurate.
- **Keep publication blocked until both findings are closed.** Rejected because it prevents collecting the exact evidence required to close them.

## Follow-up

A native stage-aware GSD gate could eventually encode this sequence. That would be a separate, generally reviewed change; this decision does not change GSD tooling or introduce a project-wide exception.
